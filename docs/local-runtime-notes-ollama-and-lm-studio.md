# Local-runtime notes: Ollama and LM Studio

- Both serve an OpenAI-compatible `/v1`, and that endpoint answers `/v1/models` with an id and nothing else — no window, no capabilities, no residency. A model discovered that way lands on `DEFAULT_CONTEXT_WINDOW` (256k). Ollama's runner is loaded at whatever its VRAM allowed (`OLLAMA_CONTEXT_LENGTH` documents the default as "4k/32k/256k based on VRAM") and **drops the oldest messages in silence** when the prompt overflows. So the harness never compacts and the conversation loses its head with nothing on the wire to say so. Reading each runtime's own listing is what makes the catalog's number true. It is the whole reason this feature exists.
- `[model_providers.<id>].models_list_dialect` picks the listing shape (`openai` default, `ollama`, `lmstudio`). `remote/local_runtime.rs` is both local dialects. Ollama needs calls (`/api/tags` for what is on disk, `/api/ps` for what is resident, `/api/show` per model for the window and capabilities). LM Studio's `/api/v1/models` carries all three in one answer, falling back to `/api/v0/models` for a build older than 0.4.0.
- vLLM needs no dialect. Its `openai` listing carries the window as `max_model_len`, and `parse_remote_model_value` reads it.
- `context_window_source` decides which of the windows reaches the catalog, and defaults to `loaded`. An UNLOADED model has no running window, so it falls back to the maximum — never to the client default. This is the guess this feature exists to remove.
- `/api/ps` lists CPU-resident runners too. `size_vram > 0` is what separates them, and a dot that claims VRAM for a CPU runner is wrong.
- The window is read through `general.architecture` (`llama.context_length`, `qwen2.context_length`). A scan for any `*.context_length` also matches a projector's, which describes a different tensor.
- **The green dot.** `ModelInfo.loaded_in_vram` is `Option<bool>` and rides `meta.loadedInVram` to the picker. The answers are distinct: a remote model writes no key and draws no dot, a loaded local model draws `theme.accent_success`, an unloaded one draws `theme.gray_dim`. Collapsing the absent case into `false` puts a cold dot beside every cloud model in the list. The dot's column is reserved for the WHOLE list (`dot_column_w`), not per row. A per-row reservation starts the label at a different column on a dotted row than on a plain one. A picker holding both local and cloud models reads as multiple ragged lists.
- `loaded_in_vram` is never persisted. It describes the runtime at one instant, and a replayed value claims a load that ended.
- The dot is POLLED, not painted once. A local runtime loads a model on its first request. The local runtime unloads it on an idle TTL, so residency read at catalog build is wrong within minutes. `refresh_local_residency` re-reads only the residency (`/api/ps`, or LM Studio's listing) on `RESIDENCY_POLL_INTERVAL`, and `apply_local_residency` pushes a models-updated ONLY when a dot actually changed. A push per tick redraws the picker of every connected client for nothing. An unreachable runtime leaves the dots as they were, because reporting every model cold will claim an unload nobody observed.
- **`extra_body` is the escape hatch, and the typed request structs are why.** `ChatCompletionRequest` and its siblings are closed, so a per-deployment setting only one target understands has nowhere else to go. LM Studio's `ttl`, Ollama's `keep_alive`, `truncate` and `options.num_ctx` are each one of those. It rides `SamplerConfig.extra_body` (per client, since it is per-model config) and merges into the serialized body through `merge_extra_body`, AFTER the builder ran. It can never displace a field the builder decided. A dotted key addresses a nested object, because TOML cannot spell a nested table inline beside scalar siblings.
- **Ollama's compat endpoint cannot carry `num_ctx` at all**, so `extra_body` alone does not fix the window there. The compat handler's request struct has no `options` member and Go discards unknown fields. Preloading with an explicit `num_ctx` and then using `/v1/chat/completions` does not work either — `runnerRef.needsReload` compares `Runner` options. An auto-`num_ctx` request against an explicitly-loaded runner triggers a reload that throws away both the preload and the warm KV cache. `api_backend = "ollama"` is the only way to pin it.
- `ApiBackend::Ollama` posts `/api/chat`, whose paths are SIBLINGS of the compat endpoint at the host root. One provider block names one base URL for both, so the client strips `/v1` when it builds its endpoint template (`native_host_root`).
- The response is NDJSON, not SSE: one whole JSON object per line, no event framing and no `[DONE]`. `ndjson_chunk_stream` reassembles lines across transport chunk boundaries and treats what is left in the buffer at end of stream as a line. This is because the last one usually arrives without a newline.
- A tool call arrives WHOLE on one line, with its arguments as an OBJECT rather than a string of fragments. `stream_ollama` emits it as a single `ToolCallDelta` carrying the complete arguments — a consumer that waits for a second fragment waits forever. Converts the object to the JSON string every other backend carries. A call Ollama gave no id still gets one. Otherwise, calls to the same tool in one message cannot be told apart by their results.
- A line carrying only `error` is a failed run. Ending the stream quietly there hands the turn a truncated answer as a finished one. Both the L2 transform and the compaction arm fail on it.
- Ollama's thinking is unsigned plain text, so its reasoning item carries no `encrypted_content` and `ThinkingReplayPlan` always replays it natively. A reasoning item and the assistant message it belongs to are items here and ONE message on that wire. Sending them apart is consecutive assistant turns in the model's own template.
- **Pricing.** A local model charges nothing and is in no catalog. The modelinfo lookup can only 404 — once per TTL, forever. `pricing_lookup_enabled = false` covers a CONFIGURED model. A DISCOVERED one is not in config at all, and `resolve_configured_pricing` rebuilds the catalog from config alone, so discovery also registers its ids with `model_pricing::suppress_lookup_for`.
- `[model_providers.ollama]` and `[model_providers.lmstudio]` with nothing in them are complete configurations. `apply_builtin_preset` fills the base URL, the dialect and the pricing switch from the id, and only where the user left them unset.
